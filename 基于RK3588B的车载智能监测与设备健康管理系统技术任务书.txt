基于正点原子 ATK-DLRK3588B 开发板的车载智能监测与设备健康管理系统技术任务书

版本：V1.0
编制日期：2026年10月20日
文档性质：项目开发与验收技术任务书。

一、项目任务与建设范围

1.1 项目任务
建设基于正点原子 ATK-DLRK3588B 开发板的车载智能监测与设备健康管理系统，完成硬件接口设计、Linux开发环境搭建、外设驱动、数据采集、故障诊断、声光告警、可视化显示、日志存储、CAN节点管理及网络通信，并形成可复现的开发和验收资料。

1.2 建设范围
系统采用RK3588单主控架构，配套MPU6050、DHT11、霍尔测速、蜂鸣器、LED、触摸显示屏及W25Q128存储模块；依据实际模拟量通道需求配置外置ADC及信号调理电路。
本任务书规定项目开发任务、功能要求、实施阶段、交付成果和验收方法。文中的性能指标属于开发及验收目标，完成情况由实板测试报告确认。

二、项目整体概述与目标

以正点原子 ATK-DLRK3588B 为主控开发平台，运行与该板卡匹配的厂商 Linux 系统，实现车辆运行状态与车载设备健康状态的采集、诊断、告警、显示、存储及远程上报。
系统采集车速、温湿度、六轴姿态、震动、关键器件模拟量及数字量，管理 CAN 下游节点在线状态，识别超速、冲击、倾斜、参数越限、传感器异常及节点离线等事件，通过蜂鸣器、LED 和屏幕提示异常，并记录带时间戳的历史数据。
本项目的碰撞监测功能指车身震动或碰撞冲击检测与告警；未配置前向测距传感器，不作为前向障碍物预测或自动制动功能。车速为零仅判定停车或静止，没有发动机运行信号时不单凭车速判定怠速。
项目目标为可在开发板及台架完成演示、测试和复现的工程原型。车规认证、整车 EMC 认证和道路安全控制不作为本任务书默认交付项。

三、系统硬件方案及接口适配

3.1 主控平台
采用正点原子 ATK-DLRK3588B 开发板，以实际板卡版本、原理图和配套 SDK 为硬件及软件适配依据。内存、存储容量以实际采购配置为准，不固定写为某一容量。
硬件连接采用RK3588对应的SoC信号名和实际连接器针脚号。同一信号接入前应核实连接器位置、复用功能、供电电压和 IO 电压域。

3.2 姿态与震动模块
实现 MPU6050，通过可用 I2C 总线接入。完成地址识别、初始化、六轴数据读取、零偏标定、姿态解算和震动指标计算。
优先使用匹配 SDK 中可用的内核驱动；若采用 i2c-dev 用户态访问，应实现统一接口，避免与内核驱动同时占用同一设备。

3.3 温湿度模块
实现 DHT11，完成接线、电平、上拉及 Linux 驱动适配。优先核查厂商内核中 DHT11/IIO 驱动的可用性。
不得以普通 Linux 用户态忙等待时序作为稳定采集的默认方案。若现有内核驱动无法可靠工作，应通过内核侧采集、驱动适配等方式解决，并以实测成功率验收。
采集周期先设为2秒，并依据实际模块数据手册核实；重试需满足器件时序，不能通过高频读取弥补失败。

3.4 霍尔车速检测
实现 JY-110 霍尔测速模块。确认其输出类型和电压，经必要的电平转换、上拉及滤波后接入 GPIO 中断或可用计数资源。
核查脉冲最高频率，优先使用内核中断计数；使用 GPIO 事件接口时应验证峰值频率下事件丢失情况，不以低频演示替代计数完整性验证。
车速公式：v(km/h)=脉冲数增量×车轮周长(m)×3.6÷每圈脉冲数÷采样时间(s)。
车轮周长、每圈脉冲数、去抖时间和无脉冲超时均为可配置参数；去抖不得过滤合法的高速脉冲。

3.5 分级声光告警
实现有源蜂鸣器与 LED，使用板载资源或外接模块。GPIO 经合适驱动电路控制外接负载，不直接承担超出 IO 能力的电流或5V负载驱动。
定义正常、预警、故障、恢复状态及短鸣、连续提示、LED 闪烁模式；支持告警确认，确认操作不应直接清除仍存在的故障。

3.6 显示与触摸
实现 LVGL 界面和功能分区，采用 LVGL 8.2 应用接口，具体依赖版本需固定。
2.8寸240×320 SPI触摸屏作为项目显示设备；确认显示控制器、触摸控制器、SPI电平和可用驱动，分别适配显示及输入。
显示输出选择厂商系统实际支持的 DRM/KMS 或 framebuffer 路径，触摸使用实际可用的输入驱动。若该屏幕无法在目标板稳定使用，再记录并批准使用兼容显示屏的变更，不默认更换屏幕。

3.7 数据存储
实现 W25Q128JV SPI Flash 作为事件日志介质，适配 SPI NOR/MTD 或专用驱动接口，禁止在已有内核驱动占用时另行直接访问同一芯片。
根据实际分区设计配置区和循环日志区，执行分页写入、按擦除块管理、序列号、长度校验及 CRC 校验。
开发板本地文件系统用于应用、配置、运行诊断及导出文件；外接Flash负责事件日志持久化。

3.8 模拟量与数字量
实现电机电流、母线电压、传感器供电、温度、液位等模拟量监测目标，以及开关、液位告警、继电器反馈等数字量监测目标。
先列出实际通道数、信号类型、量程、精度和采样率，核对开发板可用 ADC 的引出资源及电压范围。资源不足时增加外置 ADC，通过 I2C/SPI 接入；采集通过Linux IIO或对应外置ADC驱动实现。
禁止将车载12V、24V或其他超量程信号直接接入 ADC/GPIO。应配置分压、保护、滤波，必要时隔离。

3.9 CAN 与以太网
实现 CAN 心跳、节点在线管理和以太网上报功能。核查板上实际 CAN 接口、收发器、复用和终端条件，软件采用 SocketCAN。
通过可用以太网接口接入上位机，实现 TCP 心跳、状态上报、参数查询及 ACK/NACK 机制。

3.10 电源与接口冻结任务
开发板供电按其厂商规格执行；电源输出电压和容量必须与整板输入要求匹配。车辆输入需经过适合实际板卡输入规格及峰值功耗的保护和稳压方案，外设按各自电压供电。
正式接线前交付接口表，至少包含：设备、板卡版本、连接器及针脚号、SoC信号名、电压域、设备树节点、驱动、Linux访问接口、复用冲突、保护电路和测试结果。
接口针脚号依据实际板卡版本及原理图确定；完成接口表并核对电气连接是第一阶段必须执行和验收的任务。

四、软件环境搭建任务

4.1 开发主机
搭建与所用厂商 SDK 要求一致的 Ubuntu Linux 开发主机或虚拟机，Windows 用于资料管理、串口和厂商烧写工具。
准备编译依赖、Git、串口工具、文件传输工具和网络调试工具。记录主机系统版本、SDK版本及工具安装步骤。

4.2 板端系统
以正点原子提供的、与实际 RK3588B 板卡匹配的 Linux SDK 及 Buildroot 镜像为基线。内核、U-Boot、设备树、根文件系统和工具链采用同一套兼容配置，不随意混用其他板型镜像。
完成 USB 烧写、串口启动日志读取、网络连接、远程登录、文件传输、显示输出和存储挂载。记录恢复模式进入方法及镜像备份、恢复步骤。

4.3 编译与依赖
采用配套 AArch64 Linux 交叉编译工具链，核对板端 ABI、libc 及动态库版本，工具链须面向AArch64 Linux用户态应用。
业务采用 C/C++、POSIX 线程、CMake/Make，按需启用 libgpiod、I2C工具、SocketCAN工具、LVGL及显示输入依赖。依赖版本与板端实际支持接口保持一致。
先完成交叉编译小程序并在板端执行，再开展整套应用构建。

4.4 内核与设备树
按需启用 GPIO、中断、I2C、SPI、SPI NOR/MTD、IIO、CAN、显示、触摸和 watchdog。检查 pinctrl、时钟、电源、片选和复用冲突。
输出内核配置差异、设备树修改、驱动适配文件及可复现的构建命令。板卡驱动已有支持时优先复用厂商实现。

4.5 启动及维护
根据实际根文件系统使用的 init 机制配置开机自启、日志、优雅退出和异常重启。不得假设所有 Buildroot 镜像均使用 systemd。
验收：主机可重新构建应用；板端可运行构建产物；重启后服务可启动；依赖清单、设备访问权限和烧写步骤可复现。

五、系统软件架构与执行任务

5.1 总体分层
硬件驱动层：管理 GPIO、I2C、SPI、ADC、CAN、显示输入和看门狗。
设备适配层：封装传感器读取、速度计数、Flash日志及故障码。
业务层：采集、滤波、阈值判断、状态机、节点管理和通信。
界面层：统一读取状态快照，展示数据及告警。
存储层：异步处理运行数据、告警及历史查询。
线程间通过有界队列、互斥锁、条件变量及状态快照通信。明确每类数据的生产者、消费者、溢出策略和有效期，避免多个消费者争抢同一条消息。

5.2 任务划分及初始目标周期
车速任务：获取脉冲计数和单调时钟时间差，每100毫秒更新计算窗口，低速可使用更长窗口或脉冲周期法。
姿态震动任务：目标50Hz采集，输出姿态、震动和数据质量状态。
温湿度任务：初始2秒采集一次，输出校验结果和有效时间。
ADC任务：根据通道扫描要求设置初始10Hz输出，实际能力以适配验证为准。
数字量任务：中断或20毫秒扫描，按输入类型配置防抖。
CAN任务：事件接收并周期发送心跳，管理节点信息。
网络任务：TCP连接、保活、上报、指令和重连。
心跳管理任务：检查各工作线程和设备数据是否按期更新。
诊断任务：事件驱动处理，必要时以50毫秒周期检查超时。
日志任务：有界队列异步写入、轮转、校验和历史读取。
GUI任务：单一线程调用LVGL；按10Hz目标刷新显示数据，图形处理按实际移植要求调度。
以上为开发目标，需在目标板和压力负载下测量。普通 Linux 调度不等于硬实时保证；无法满足指标时先定位驱动、负载及调度瓶颈，再决定是否采用实时内核等措施。

5.3 数据结构与时间
车辆状态与日志结构包含速度、温湿度、俯仰角、横滚角、告警、设备来源、单位、有效标志、采样时间、序列号及错误码。
超时、采样间隔及延迟使用单调时钟；历史展示使用系统日历时间，并记录时钟是否同步。传感器断开不得以0值伪装为正常测量值。

六、核心功能执行及验收要求

6.1 车速监测与超速告警
执行：实现脉冲计数、周长标定、速度换算、去抖、静止判定及超速阈值配置，采用80km/h作为台架演示初始值。
验收：使用已知频率脉冲输入，覆盖低、中、高频和设计峰值；各点持续60秒，记录理论计数与实测计数。稳定输入时速度换算相对误差目标不超过5%，计数误差目标不超过1%；零频输入在配置超时后显示静止。越限后产生告警、界面提示及日志，恢复后按滞回规则解除。

6.2 姿态与震动监测
执行：完成六轴读取、零偏校准、俯仰/横滚解算、滤波及冲击事件识别。实现15度倾斜作为初始演示阈值。
震动阈值必须有明确物理单位；明确量程、g或m/s²单位、滤波方式和持续时间后重新标定。
验收：静置及已知角度夹具测试0、正负15度、正负30度，稳定后角度误差目标不超过3度；受控振动、倾斜及冲击分别可触发对应事件。断开设备后显示失效并记录故障，不继续展示旧数据为实时值。

6.3 温湿度监测
执行：完成DHT11读取、校验、重试、超时及界面更新。
验收：正常台架环境连续采集30分钟，成功率目标不低于95%，记录失败次数与原因；与参考仪表的差异按所用DHT11型号数据手册精度评价。断开与恢复设备均产生明确状态变化。

6.4 ADC与数字量监测
执行：逐通道标定量程、增益、偏置、单位、阈值和数字量有效电平，实现滤波及异常识别。
验收：每个模拟量通道至少测试量程内5点，误差满足该通道规格表；数字输入逐路验证正常、触发、抖动和恢复。缺失实际车载信号时可使用校准信号源台架注入，记录注入位置及换算过程。

6.5 CAN节点管理
执行：采用心跳协议思路，明确帧ID、节点ID、心跳周期、序列号、状态字段和可选应用层校验的实际字节布局，标准CAN载荷不得超过其帧格式允许长度。
初始台架配置：500kbit/s、心跳周期1秒、离线阈值3秒；最终双方配置必须一致。
验收：至少2个逻辑下游节点同时在线，逐一停止心跳、恢复发送和注入异常报文；离线判定应在阈值后一个检查周期内完成，其他节点正常运行。记录断线及总线异常后的恢复行为。

6.6 网络上报与远程查询
执行：定义帧头、版本、命令、长度、序列号、载荷、CRC、ACK/NACK，明确字节序、CRC参数、最大报文长度及TCP流拆包粘包处理。
支持状态上报、心跳、参数读取及允许范围内的参数设置，验证数据长度、命令和参数范围。
验收：上位机连续收发30分钟；分片、合并、错误CRC和非法长度均能正确处理。断网60秒后恢复，在网络和服务端就绪后30秒内恢复通信；若缓存告警，明确容量及重传去重策略，不能宣称无限缓存。

6.7 分级故障与声光告警
执行：统一正常→预警→故障→恢复状态机，为速度、倾斜、震动、模拟量、数字量、传感器失效、节点离线设置等级、持续时间和滞回条件。
验收：逐类注入异常，核对事件类型、等级、蜂鸣器、LED、界面和日志；同时注入多故障，不能因单一优先级分支丢失其他故障。
从有效数据进入诊断模块至声光输出的延迟，连续100次台架测试P95目标不超过200毫秒，同时报告最大值。该指标不包含传感器自身采样等待，温湿度等端到端延迟应另按采样周期统计。

6.8 日志存储与回溯
执行：实现事件触发、异步写入、分页循环存储、按需擦写及Flash寿命管理。普通数据按配置周期记录，告警变化单独记录，避免每轮诊断重复写同一告警。
验收：写满预定日志区并验证循环覆盖；查询至少1000条记录；校验内容、序列号、时间、类型和CRC。实施10次台架随机断电重启，已确认持久化记录应保持可读；未提交的最后一条允许丢失，但不得导致整个日志区不可解析。记录损坏时应可识别并恢复到有效边界。

6.9 LVGL车载界面
执行：实现速度区、温湿度区、姿态区、状态栏、告警查询页，增加设备健康管理所需的模拟量、数字量、节点在线和网络状态显示。
验收：实际屏幕可显示全部必需信息，可翻页查历史；数据目标10Hz更新，温湿度按自身周期更新；连续交互30分钟无崩溃、文字截断和明显阻塞。设备失效时显示无效或离线状态，不显示伪正常数值。

6.10 系统可靠性
执行：配置硬件看门狗及应用健康检查，检查关键线程是否持续前进，不能只由独立喂狗线程无条件喂狗。依据实际硬件支持配置，记录实际看门狗设备、超时及复位机制。
验收：台架连续运行24小时，无非预期退出或重启，记录CPU、内存、温度、采集成功率、队列积压和日志情况。注入关键线程卡死、传感器掉线、网络中断和存储写失败，验证告警、恢复和必要时重启。
开发负载下的24小时测试不等于整车环境及车规验证，不预先写成“已经满足长期车载可靠性”。

七、关键技术与优化任务

7.1 电源与抗干扰
实现供电稳压滤波、信号保护、地线规划、传感器滤波和霍尔防抖。依据实际线束、负载及电源条件制定台架干扰测试；报告具体条件和现象，不使用未经测试的“杜绝误报”等绝对结论。
7.2 调度与数据解耦
界面、网络和Flash耗时操作不得持有采集共享锁长期阻塞。使用有界队列，分别规定普通样本丢弃策略、关键事件保护策略和过载计数。
7.3 故障恢复
对设备打开失败、读取失败、CAN异常、TCP断线及Flash错误分别设置超时、重试间隔和恢复状态，不允许无限忙循环重试。
7.4 数据及存储
统一物理单位、标定参数、时钟来源及版本；配置变更应校验并持久化。导出记录应能追溯软件版本和配置版本。

八、软件工程组织与模块职责

8.1 程序入口与运行管理
main：负责配置加载、设备初始化、线程创建、资源检查、信号处理、优雅退出及应用健康监测。
config：集中管理采样周期、车轮参数、告警阈值、CAN节点、网络地址、日志容量及参数版本，启动时检查配置合法性。

8.2 设备访问与采集模块
platform：封装Linux GPIO、I2C、SPI、IIO、SocketCAN、MTD、输入设备及看门狗访问，统一错误码和资源释放接口。
speed：提供霍尔计数、时间差计算、防抖、速度换算和静止检测。
attitude：提供MPU6050初始化、标定、六轴读取、姿态解算和震动指标。
environment：提供DHT11读取、校验、失败重试和数据有效性管理。
adc：提供通道扫描、量程标定、滤波及物理量换算。
digital_input：提供开关量状态读取、防抖及边沿事件。

8.3 业务模块
can_node：提供CAN报文解析、心跳收发、节点状态和总线错误处理。
network：采用Linux socket实现TCP连接、报文编解码、应答、重连和状态上报。
diagnosis：提供统一故障状态机、阈值滞回、多故障管理及事件发布。
alarm：根据告警等级控制蜂鸣器和LED，采用非阻塞模式执行提示节奏。
health：检查线程进度和设备数据有效期，执行恢复策略并协调看门狗。

8.4 存储与界面模块
storage：提供W25Q128日志分区、擦写、校验、循环管理和断电恢复。
log_service：提供有界日志队列、异步提交、历史查询及文件导出。
gui：提供LVGL仪表主页、设备健康页、节点状态页、告警历史页和参数设置页，图形接口由统一线程调用。
state_store：提供带时间戳和有效标志的状态快照，供诊断、界面和上报模块读取。

8.5 通用组件与部署
utils：提供CRC、滤波、单调时间、字节序转换和数据校验。
build：提供CMake/Make构建、交叉编译配置及依赖版本说明。
deploy：提供安装、开机启动、停止、版本查询和应用恢复脚本。基础交付包含应用部署与恢复；完整系统OTA及引导回滚不属于本期必需功能。
tests：提供协议测试、信号注入、日志完整性和故障恢复的测试工具及步骤。

九、实施阶段及阶段验收

阶段一：资料与接口冻结
执行板卡版本确认、SDK选择、现有模块清点、信号规格及引脚表编制。
验收接口表、硬件连接图、通道规格表、版本清单及必要的模块采购清单。
阶段二：环境搭建
执行主机安装、镜像备份及烧写、串口网络调试、交叉编译和程序部署。
验收可复现环境说明、板端运行样例及构建日志。
阶段三：驱动与单模块适配
执行GPIO、I2C、SPI、霍尔、DHT11、ADC、CAN、屏幕及Flash验证。
验收各模块独立测试记录；失败项先解决或形成明确硬件变更，不进入伪装完整功能的集成验收。
阶段四：业务及界面集成
执行多线程、状态快照、故障状态机、告警、日志、上报及LVGL集成。
验收正常、异常、恢复和并发场景全部贯通。
阶段五：系统测试与交付
执行第六章全部验收项及24小时稳定性测试，修复问题，形成交付版本。
各阶段按依赖推进，不在尚未完成硬件确认时承诺固定日历工期。

十一、总体验收判定

第六章每项均须有执行步骤、输入条件、预期结果、实际结果和证据文件。达到全部必需功能及指标，并能根据文档在同型板卡恢复环境、构建和运行后，方可判定项目原型验收通过。
任务书中明确需在接口冻结阶段形成的通道规格、接线和电压参数，应在接线及实现前完成并纳入版本管理；不得在验收时临时降低要求。
仿真、回放或注入测试必须标注。它们可用于联调与故障复现，但不能替代真实传感器、CAN物理链路、显示屏和Flash的硬件验收。
